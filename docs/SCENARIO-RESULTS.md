# Scenario results

The seven mandatory scenarios. Each is a repeatable test or script, and every number below
is quoted from evidence the run recorded (`evidence/*.json`, regenerated by `npm test`,
`npm run scenario:6-live`, `npm run scenario:7` and `scripts/production-lifecycle.ts`). CI
runs all of them on every push. The first fully green CI run with the live and upgrade steps:
[run 41735822020](https://github.com/rkendel1/felt-ops/actions/runs/41735822020) (`af27efc`).

## 1. Business policy change (`tests/scenario-1-policy.test.ts`)

- **Initial conditions:** purchasing policy v1 (≤5,000 manager; ≤25,000 manager → finance;
  above: manager → finance → executive). A 12,000 request is pending under v1.
- **Actors and authority:**
  - Fiona (finance role: `policy.propose`) proposes.
  - Maria (CFO: `policy.approve` and a `policy.approve.finance` grant) approves.
  - Priya (operations) and Rhea (finance, no grant) are refused.
- **Objective:** lower the thresholds without a deployment. Approvals above 10,000 need an
  executive.
- **Failure conditions exercised:**
  - malformed rules → `INVALID_ARGUMENT`;
  - Priya proposing → `FORBIDDEN`;
  - Fiona approving her own change → `FORBIDDEN`;
  - Rhea approving → `FORBIDDEN`.
- **Expected and observed:**
  - The impact preview lists the workflows and the amounts whose chain changes (4,999; 5,000;
    12,000; 24,999; 25,000).
  - A request submitted while v2 is a draft follows v1.
  - After approval, 12,000 needs manager → finance → executive, and 3,000 needs manager →
    finance.
  - The earlier request keeps v1.
  - No release or deployment exists.
- **Verification (computed):** `policies.verify` → `ok: true`. Every request since approval
  carries v2 and its chain (2 requests checked).
- **Evidence:** `evidence/scenario-1.json`. The change history is
  `change.requested → change.approved → change.verified`.
- **Found while building it:** F-014 (retroactive approval), fixed.

## 3. Production incident (`tests/scenario-3-incident.test.ts`)

- **Initial conditions:** R1's actual source (`171b6e3`, extracted from git history) runs on
  a FeltDB state directory. AP enters two Northwind invoices by hand, and the supplier feed
  delivers them again (numbers formatted differently). Two duplicate commitments result
  (7,950.00).
- **Actors:**
  - Integration Sentry (detects, opens the incident).
  - Eli (investigates, root cause, change CR).
  - Ledger Reconciler (proposes reversals).
  - Rhea and Maria (approve); Priya (refused); Fiona (approves a wrong proposal).
  - Otto (verifies the assignment).
- **Phase B, current source on the same state:**
  - The incident is opened by the agent; a repeated detection joins it.
  - A third cross-channel copy is held as an exception by the fix, so no new duplicate.
  - The agent's direct reversal attempt is refused (`FORBIDDEN … approval`).
  - Three proposals are made. Priya's approval is refused (no `feltkit.agent.write`). Rhea and
    Maria approve two: they run **as `agent:agent-ledger`**, determined by dispatch. A
    duplicate approval runs nothing.
  - The third proposal (a legitimate commitment) is approved by Fiona and fails at execution:
    "The reconciliation does not identify this commitment as a duplicate". The commitment is
    untouched.
- **Verification:**
  - The assignment verifier (`reconciliation-clean`) passes.
  - Exactly 7,950.00 was reversed.
  - The incident resolves only because its process check passes; then the review is recorded.
- **Evidence:** `evidence/scenario-3.json` (FeltKit action records with proposer, approver,
  executor and error; 11 checkpoints; incident timeline).
- **Found:** F-012 (R1 could not approve Operations purchases), F-008 (the approver is absent
  from CompanyOS's own record).

## 4. External integration change (`tests/scenario-4-integration.test.ts`)

- **Initial conditions:** Northwind link on API v1, healthy, synced through 2026-10-31.
  The test supplier runs at a real HTTP port.
- **Flow:**
  1. The v1 sync imports NW-8001 and NW-8002.
  2. The supplier retires v1 and issues NW-8003.
  3. The next v1 call fails with `UPSTREAM_REJECTED … (410)`. The link becomes `failing`,
     and the watermark holds at 2026-11-01T15:00.
  4. The agent opens an incident and isolates the link.
  5. Restore is refused until v2 is validated ("No successful v2 call has been recorded since
     the link was isolated").
  6. The operator adds context and resumes. The v2 validation call imports nothing while the
     link is isolated.
  7. The engineer restores on v2, and the next sync imports NW-8003 only.
- **Verification:**
  - The supplier's invoice list equals CompanyOS's (`NW-8001`, `NW-8002` via v1; `NW-8003`
    via v2, each once).
  - The link is healthy on v2, with no duplicates.
  - The assignment is verified and the incident resolved.
- **Evidence:** `evidence/scenario-4.json`, including every request the supplier received.
- **Partial:** the v2 operation was declared in the integration from R1. The engineering step
  is tracked (change CR) and validated by a real call, but is not a new commit.
- **Found:** F-018 (silent `onOutcome` failure) and F-019 (payload shape). On the first run
  nothing was imported while everything reported success.

## 5. Organizational change (`tests/scenario-5-departure.test.ts`)

- **Initial conditions:** Fiona Walsh holds 3 active grants (manager FIN ≤25,000, finance
  ≤100,000, invoice ≤50,000), 2 pending Finance approvals and 1 open work item.
- **Flow:**
  1. Ivy assigns the Access Steward (permitted: `org.responsibilities`, `org.depart`).
  2. The agent's inventory runs as an observation.
  3. The direct `org.depart` call is refused (approval required). The proposal follows.
  4. Otto (operator, no `org.access`) cannot approve. Ivy approves, and it runs as the agent:
     `grantsTransferred: 3, approvalsMoved: 2, workMoved: 1`.
- **Access:** CompanyOS refuses Fiona at once ("left the company on 2026-11-07"). Her FeltKit
  session was then revoked (`revokePrincipal` → 1). In production this is a CLI step requiring
  a stop (F-011/F-023), and her account itself cannot be disabled (F-010).
- **Continuity:**
  - Rhea holds the transferred grants (`transferredFrom` set) and decides the moved 14,250
    approval.
  - Fiona's ended grants, past decisions and person history are intact.
  - Proposing the departure again fails ("already left").
- **Verification:** `departure-complete` passes.
- **Evidence:** `evidence/scenario-5.json`.

## 6. Agent failure and recovery (`tests/scenario-6-recovery.test.ts`, `scripts/scenario-6-live.ts`)

- **Initial conditions:** R1 produced 4 duplicate commitments.
- **Live run (real processes over `/mcp`, `evidence/scenario-6-live.json`):**
  1. The primary agent process proposes 4 reversals. Rhea approves 2, and the process exits
     abruptly with **137** (fault injection) before reporting.
  2. Its session is revoked; replaying its token at `/mcp` gets **HTTP 401**.
  3. The operator's view disagrees, and the records settle it:
     - The agent's last statement: "4 reversal(s) proposed; waiting for Finance approval".
     - FeltKit: `succeeded, succeeded, proposed, proposed`.
     - The records check: 2 duplicates remain.
  4. Recovery: suspend → cancel the FeltKit task → reassign to the standby. The standby
     process proposes only the remaining 2, Maria approves, and it completes (exit 0).
  5. Result: **exactly four reversals, each once** (two by each agent). The assignment is
     verified from records.
- **In-process run adds:**
  - A platform restart with `reconcile()` before recovery.
  - A stale replay of an already-reversed commitment, refused at execution ("already
    reversed").
  - The orphan-approval case:
    - Under production semantics the owner is unresolvable (`resolvePrincipal` → null), so
      approval fails closed.
    - In dev/test the declared dev agent *is* resolved (F-022), so the approval would run.
    - CompanyOS's suspension makes it fail ("Agent agent-ledger is suspended"), and nothing
      changes.
- **Result:** Verified. Not exercised: an action left `interrupted` (outcome unknown), which
  needs a crash *during* execution. FeltKit's own suite covers it (GUARANTEES.md, Agents).

## 7. Platform upgrade (`scripts/scenario-7-platform-upgrade.ts`)

- **Discovery (npm, live):**
  - `@feltdb/feltkit` 0.3.13 = latest.
  - `@feltdb/core` 0.21.0 = latest.
  - `@appport/sdk` installed 1.4.0, latest **1.4.1**, but FeltKit pins it exactly, so it cannot
    be adopted (F-001).
  - `@appport/services` 0.14.0 = latest.
- **Old platform:**
  - FeltKit **0.3.12** with FeltDB **0.20.0** (npm `overrides`), installed from npm.
  - CompanyOS seeded and production activity performed (PR-0040 approved and ordered).
  - Platform change CR-0001 recorded and a data baseline captured by CompanyOS.
- **Tests on the new platform (0.3.13 + 0.21.0):** 9/9 passed, recorded as test-run evidence.
- **Upgrade:** the new platform opened the old state with schema status **`current`** (same
  contract, no migration).
- **Lifecycle:** assessed → tested → approved (CEO) → release `platform-0.3.13` (a platform-only
  release) → deployed → `verifyData` passed with no differences → verified. Reconciliation
  and policy resolution still work on the upgraded data.
- **Evidence:** `evidence/scenario-7.json`.
- **Limit:** "deployment" here is the new platform opening the production state, which is what
  `feltkit start` does. It was not a full artifact deploy of the old platform.
